# 量测数据（`probe/` 产出）

本目录是 `probe/` 夹具产出的采样结果。判定口径、根因结论与实测数字见 `交接文档.md` §4.6 / §4.10。

⚠️ 本目录下的**量测产物不入仓**（`.gitignore` 里忽略 `/probe/traces/`），但**本 README 例外入仓**
（见 `.gitignore` 的 `!/probe/traces/README.md`）——判定口径要跟着代码走，否则新克隆的仓库会缺这份文档。
需要长期保留的样本，请先把结论写进 `交接文档.md`。

## 两类产物

| 文件 | 来源 | 用途 |
|---|---|---|
| `cap-*.csv` | `capture.ps1` 屏幕捕获 | 挂件滚轮缩放抖动（逐帧像素指标） |
| `run-*.json` | 探针回传（`POST /__aqm/trace`） | `layout`=布局报告 / `measure`=元素量测 / 缩放逐帧采样 |

⚠️ 取 `run-*.json` 时**注意区分窗口**：挂件窗与主窗口都会响应触发器（`viewport.w` < 400 为挂件窗）。
早期只有主窗口接了量测，导致排查挂件内控件时拿到的全是主窗口那份（白等了好几轮）。

## 判定口径

每份 `cap-*.csv` 一行 = 一帧屏幕捕获（GDI `CopyFromScreen`，60fps，DPI 感知）：

| 列 | 含义 |
|---|---|
| `t_ms` | 相对捕获开始的毫秒 |
| `mx0,my0,mx1,my1,mw,mh` | 品红底块的像素 bbox（= 挂件内容实际渲染到屏幕上的矩形） |
| `hx,hy,hn` | 黑块质心（硬阈值：三通道 <60） |
| `kx,ky` | 黑块质心（两遍法的第二遍：①定位后 ±25px 内亮度加权，亚像素） |

**核心指标**：黑块画在「滚轮锚点」对应的画布坐标上 —— 鼠标焦点缩放下它应当**在屏幕上纹丝不动**。
把它按帧分成两类：
- **尺寸变化帧**（`mw` 与上一帧不同）→ 抖动出现在这里，看 `kx` 偏差
- **静止帧** → 偏差即**量测噪声底**（衡量该份数据是否可信）

**先看静止帧**：噪声底若明显高于其它样本（如 0.13 vs 0.02），说明该轮捕获受外部负载干扰，其抖动数字不可直接采信。

## 有效证据（保留）

| 文件 | 说明 | 尺寸变化帧 抖动均值/峰值(px) | 静止底(px) | 时长(ms) |
|---|---|---|---|---|
| `cap-base-1.csv` | 原始代码基线（标准场景） | 1.53 / 3.0 | 0.06 | ~400 |
| `cap-fixed-2.csv`、`cap-fixed2-3.csv` | 「顺序修复」尝试 | 0.29 / 1.5 | 0.06 | — |
| `cap-legacy-20/21/22.csv` | 内容层在窗口落地后写（n=3） | 0.99 中位 / 1.5 | 0.08 | — |
| `cap-fixed-23/24/25.csv` | 内容层与窗口几何同任务（n=3） | 1.04 中位 / 2.0 | 0.08 | — |
| `cap-step10-31.csv` | 旧策略·快速滚动（单步≈9 物理像素） | **3.94 / 5.0** | 0.08 | ~300 |
| `cap-bal2-std-110/111/112.csv` | **最终版·标准场景**（+60 逻辑px，n=3） | **0.286 中位 / 1.58** | 0.03 | 517~533 |
| `cap-bal2-fast-113/114.csv` | **最终版·快速滚动**（+100 逻辑px，n=2） | **0.285 / 0.53** | 0.07 | 399 |

最终版 = `GEOM_DELAY_FRAMES=1`（窗口几何晚一帧发布）+ `MAX_STEP=6`/`STEP_FRAMES=4`。
对照：仅压小步长（step≤2、无延后）= 标准 0.64 / 666ms、快速 0.87 / 932ms ——
**几何延后让抖动和时长同时下降**，不再需要"速度换平滑"。

**尺寸跨度**可用于自检量测是否有效：标准场景应恰好 +75 物理 px（=+60 逻辑），快速场景 +125 物理 px（=+100 逻辑）。
若明显偏小，说明泵被中途腰斩（见交接文档 §4.6 的 400ms 阈值 bug）或窗口漂出捕获区域。

**静止底（噪声底）是先看的指标**：明显高于其它样本（如 0.5 或 8）说明该轮捕获受外部干扰
（人为操作挂件 / 前台窗口争夺），其抖动数字不可采信。本轮 10 份样本中曾出现 3 份此类废样本。

**三个关键结论**：
1. `legacy-20..22` vs `fixed-23..25`：**内容层与窗口几何的写入顺序（同一任务内）无影响**（0.99 vs 1.04，n=3 同口径）。
   → 早期仅凭单次样本得出的「顺序即修复、改善 5.3 倍」是错的（那次对照的两份数据起点位置不同、不可比）。
2. `step10-31`（单步 9px，抖 3.94/5.0）vs `bal2-fast`（单步 ≤6px + 几何延后，抖 0.285/0.53）：
   → 抖动**与单帧窗口位移成正比**，但**把窗口几何延后一帧可以让错位归零**，从而放大步长换速度。
3. 「几何延后」的代价可用探针逐帧数据量化：`内容层 cs×308 − 窗口 innerWidth` 在 0~9px 间波动，
   即内容在窗口右/下边缘被裁掉一条（可见框仍由窗口驱动、平滑增长）。

## 已删除的无效采样（教训保留）

以下几类已删除，重新测量时务必避免重蹈：

- **窗口漂移跑出捕获区域**：锚点缩放必然让窗口向左上漂移，早期夹具每轮不归位，几轮后挂件越出捕获区域，
  量到的 `mw` 是**被裁剪**的方块（表现为 `mx0=0`/`my0=0`）。这批数据曾导致错误结论。
  → 现夹具每轮先 `normalizePos` 归位，分析脚本也强制校验裁剪。
- **缩放幅度过小**：`deltaY=10` 时每格仅 1px，总位移 6px，抖动落在量测噪声底内，无法区分信号与噪声。
- **真值参考**：`run-*.json` 是探针从页面内采样的逐帧数据（`innerWidth` / 画布 transform / resize 计数）。
  其中 `画布scale×308 == innerWidth` 在**每一帧严格成立** —— 这是「内容层与窗口层没有失同步」的直接证据，
  也是把根因判定为「DWM 即时应用窗口几何 vs 内容层下一帧才上屏」而不是 JS 侧 bug 的依据。
